## 5. 权威关系

- 产品/范围/规则冲突：以 `PROJECT.md` 为准。
- 设计/数据冲突：以 `DESIGN.md` 为准。
- 流程/规则冲突：以 `AGENTS.md` + `DEVELOPMENT.md` 为准。
- 任务/状态冲突：以 `ROADMAP.md` + `PROJECT.md` 当前状态 + Git 实际状态为准。
- 验收冲突：以 `ACCEPTANCE.md` + `PROJECT.md` 成功标准为准。
- 文档索引/维护规则：以本页为准。

## 6. 维护规则

1. 一份文档一个关注点；不创建按阶段/按窗口复制的状态文档。
2. 决策文档（`PROJECT.md`、`DESIGN.md`、`ROADMAP.md`）顶部写 `最后更新 / 状态 / 确认记录`；未确认只能是草案。
3. 每份文档顶部"最后更新"精确到分钟。
4. 所有非用户原话推导出的规则/边界/权限/指标/字段/范围，必须打 `[推断 I#：…]` 并登记到 `PROJECT.md`；`待校准` 未清零不得进入下一阶段。
5. 行为/范围变化：更新 `PROJECT.md`、`ACCEPTANCE.md`、`README.md`（如对外）。
6. 结构/流程/数据变化：更新 `DESIGN.md`。
7. 命令/工具链变化：更新 `DEVELOPMENT.md`、`AGENTS.md`、本页检查命令。
8. 每个任务结束：更新 `ROADMAP.md`、`PROJECT.md` 当前状态。
9. 每个里程碑结束：更新 `ROADMAP.md` 的"里程碑记录"。
10. 用户中断/改需求：更新 `PROJECT.md` 的"变更记录"；受影响文档退回草案。
11. 文档移动/删除后，检查所有链接并运行 `npm run docs:check`。
12. 不写 API Key、密码、签名口令、用户隐私数据、生产数据。
13. 不要求用户提供开发所需的实际文件；参考图/参考文档可读取，但不复制进项目，只记来源和用途。

## 8. 新增文档审批

默认只有 8 份文档。需要新增时，先发申请：

```text
文档名：
目的：
为什么现有 8 份放不下：
维护成本/更新频率：
不新增的后果：
```

用户明确同意后才创建，并在本页索引和 `PROJECT.md` 变更记录登记。没有批准的新文档视为流程违规。

## 9. 文档检查

```text
npm run docs:check
```

该命令校验必需文档存在、"最后更新"精确到分钟、`npm run` 脚本引用有效、Markdown 链接和样例路径存在。文档结构变化时同步更新 `scripts/check-docs.mjs`（M1-T1 任务范围）。

如果没有自动检查，至少手动确认：

- 本页索引覆盖所有文档；
- 所有相对链接能打开；
- 没有未解释的 `TBD` / `待定`；
- 推断项没有 `待校准`；
- 图和表能渲染/显示。
